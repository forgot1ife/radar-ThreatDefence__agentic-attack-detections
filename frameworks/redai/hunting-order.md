# Where to start

1. **Check your own hosts first.** RedAI is a white-box tool: it needs the application's source code, so the people who run it are usually developers or application security staff with access to that code. Run `01-redai-on-a-host.kql` (or the Sigma process and file rules) for `bun <...>/bin/redai`, Chrome with `--user-data-dir` under `~/.redai/`, simulators named `redai-template-*` or `redai-<run>-<job>`, and files under `~/.redai/runs/`.
2. **Find out what was tested.** On a host with a hit, `~/.redai/validator-environments/<id>/environment.json` holds the App URL (`browser.appUrl`) or the iOS bundle id, and `~/.redai/runs/<runId>/run.json` the source directory. Run `03-redai-browser-and-agent-traffic.kql` to list the addresses RedAI's browser and agents reached. A production URL there means validator agents tried to exploit findings against production, signed in as the account used during setup.
3. **Read the evidence.** `~/.redai/runs/<runId>/report.md` lists every finding with the payloads tried; `artifacts/validation/<jobId>/` holds the PoC scripts and screenshots, and `artifacts/transcripts/*.jsonl` the agents' full sessions, including every shell command they ran. Scan with the YARA rules to find copies of reports or run folders elsewhere.
4. **Check the browser profile.** The profiles in `~/.redai/validator-environments/<name>/browser-profile` and `~/.redai/runs/<runId>/validation/browser-profile` hold a live session for the target application. Treat them like credentials: if the host or the folder was shared, end those sessions.
5. **Run the watchlist sweep** (hunt 02) for RedAI's paths, simulator names, package name and prompt strings on the rest of your hosts. Do not look for it in web or WAF logs: its requests carry nothing of its own.
