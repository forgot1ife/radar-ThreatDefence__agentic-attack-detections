# Where to start

1. **On your applications**, search web, WAF and proxy logs for the user agent `ARIA-X/<version> (authorized security research)` with the analytics rule, hunt 02 or Suricata 3819401. It is sent on every request of ARIA-X's own HTTP tools, so a hit is close to certain. Hunt 02 also lists what the same address sent in the following day, which covers the shell tools that do not carry the user agent.
2. **Check your own hosts** with hunt 01: `python -m aria_x` and `aria-x run|serve|demo`, `docker run ... --name aria-x-<12 hex> ... -w /work ... bash -lc`, `bash -lc` children of the ARIA-X process, and `aria-x.db` or `runs/run_<id>/work/evidence/` files. If ARTEX's port-8787 hunts fire, the command line tells you whether it is ARIA-X.
3. **Look for exposed consoles** with the Suricata server rules and the Shodan queries in `exposure/shodan-queries.csv` (title `ARIA-X · Engagement Console`, banner `Server: ARIA-X`). Its Docker image binds 0.0.0.0, and without `ARIA_X_AUTH_TOKEN` the API lets anyone start runs whose commands execute on that host; Suricata 3819414 flags a console that reports `"auth_required": false`.
4. **Search proxy logs** with hunt 02 for console API use (`/api/projects/p_<id>/runs`, `/api/runs/run_<id>/stop`, `/api/export/p_<id>`) and, with TLS inspection, the research searches to `html.duckduckgo.com` that carry the ARIA-X user agent.
