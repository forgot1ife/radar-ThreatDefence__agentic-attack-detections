# Where to start

1. **Look for the NPS client hand-off on your hosts** (the analytics rule, hunt 04, Sigma `proc_creation_breachweave_nps_client_staging`, Suricata 3819319 and 3819320): certutil, curl or wget fetching `/files/nps/npc_windows_amd64.exe` or `/files/nps/npc_linux_amd64`, or any process with `-server=` and `-vkey=auto`. That is the step where BreachWeave's skills turn a web shell into a foothold, and the commands are copied from the skills.
2. **Look for the Redis web root pages** (hunt 03, Sigma `web_breachweave_redis_webroot_pages`, Suricata 3819316 to 3819318, YARA `BreachWeave_Redis_Webroot_Pages`): requests for `redis_test.php`, `redis_diag.php` or `redis_exec.php`, a POST body of exactly `cmd=RCOK`, or a page that answers `DIAG_START` with `disable_functions` and `com_loaded`. On the server, a Redis dump file in the web root with PHP inside.
3. **Check your networks for exposed consoles** (Suricata 3819301 to 3819309, 3819321 and 3819322, the Shodan queries): page titles `tch-agent` or `BreachWeave`, `{"registrationEnabled":true}`, and calls to `/api/runtime/solvers/<id>/command` or `/api/config/host-settings`. A `main` console has no login: anyone who reaches it can read the model keys, start containers and run shell commands.
4. **Check your own hosts** for `tch-solver-<id>` containers, the `tch-agent:latest` image, `/opt/tch-agent/tch-agent solver rpc` and `~/.tch-agent/` (hunt 01, Sigma process and file rules, YARA). Read `~/.tch-agent/config/provider-prefs.json` and `settings.json` to see which model keys and contest tokens it holds.
5. **If you run an AI gateway or inspect TLS**, look for the observer, planner and search prompts and the Kimi `$web_search` request shape (Suricata 3819310 to 3819314).
6. **Sweep the watchlist** (hunt 02) for the file names, paths and URIs.
